1. 共享包设计 — 什么该抽，什么不该抽

Monorepo 最大的诱惑是"把所有共享代码都抽成包"，但这正是走向地狱的路。

✅ 应该抽成共享包的

• 多个应用真正共用的工具函数

• 类型定义（DTO、API 响应类型）

• UI 组件库（Button、Modal、Table）

• 业务常量（枚举、配置）

• ESLint / TSConfig / Prettier 配置

❌ 不应该抽成共享包的

• 只有一个应用用到的代码

• 带业务上下文的状态管理逻辑

• 还没想清楚的"将来可能共用"

• 过度抽象的"万能工具"

• 各自差异很大的"公共"组件

💡 一个判断原则

"两个应用用，就抽。只有一个用，留着。"
提前抽象是万恶之源。宁可先复制，等第三个地方用到时再抽——那时候你才真正知道 "共享接口"应该长什么样。

2. 共享包的标准目录结构

一个好的共享包应该有清晰的入口和职责。以下是推荐结构：

packages/shared-utils/
├── package.json              ← name + main + types + exports
├── tsconfig.json             ← 继承根配置
├── src/
│   ├── index.ts              ← 统一导出（桶文件）
│   ├── format.ts             ← 格式化相关
│   ├── validate.ts           ← 校验相关
│   └── __tests__/            ← 单元测试
│       ├── format.test.ts
│       └── validate.test.ts
└── README.md                 ← 这个包是干什么的
🔑 关键：统一导出（Barrel Export）

src/index.ts 是包的"门面"，把所有要暴露的内容从这里统一导出：
使用者只需要 import { formatDate, validateEmail } from '@my-monorepo/shared-utils' 一行，不用关心内部文件结构。

packages/shared-utils/src/index.ts（完整示例）
// ── 统一导出文件（桶文件 / Barrel File）──

// 格式化工具
export { formatDate, formatCurrency, formatFileSize } from './format';

// 校验工具
export { validateEmail, validatePhone, validateIdCard } from './validate';

// 类型定义
export type { UserInfo, ApiResponse, PaginationParams } from './types';

// 常量
export { API_BASE_URL, PAGE_SIZE, DATE_FORMAT } from './constants';

3. TypeScript 在 Monorepo 中的配置策略

这是 Monorepo 中最容易翻车的地方。思路是：一个 base 配置管全局，每个包只写自己 特殊的东西。

📐 三层 TSConfig 架构
tsconfig.base.json（基础配置 · 所有包共用）
tsconfig.json
packages/shared-utils
tsconfig.json
apps/admin
tsconfig.json
apps/server

第①步：根目录创建 tsconfig.base.json

my-monorepo/tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}

第②步：每个子包继承 base

packages/shared-utils/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src"]
}
apps/admin/tsconfig.json（Vue 3 前端，Vite 创建时就有，只需确认 extends）
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "jsx": "preserve",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src/**/*.ts", "src/**/*.vue"],
  "references": [{ "path": "./tsconfig.node.json" }]
}
⚠️ 关键坑：跨包引用时 import 路径怎么写？

在 admin 里引用 shared-utils，不要写 '../../packages/shared-utils/src' 这样的相对路径！
正确做法：import { formatDate } from '@my-monorepo/shared-utils'。
pnpm 的 workspace 链接会自动把包名映射到实际目录，TypeScript 也能正确解析 package.json 中的 "types" 或 "main" 字段。

4. 实战：给 shared-utils 加上 TypeScript

接第 2 课的项目，我们给 shared-utils 升级为 TypeScript 版本。

1

在 shared-utils 中安装 TypeScript（开发依赖）

pnpm add -D typescript --filter @my-monorepo/shared-utils
2

补充 package.json 中的类型入口

packages/shared-utils/package.json
{
  "name": "@my-monorepo/shared-utils",
  "version": "1.0.0",
  "private": true,
  "main": "./src/index.ts",        ← Node.js 解析入口
  "types": "./src/index.ts",       ← TypeScript 类型入口
  "exports": {
    ".": "./src/index.ts"          ← 现代 ESM 导出
  },
  "scripts": {
    "typecheck": "tsc --noEmit"
  }
}
3

把 index.ts 升级为真正的 TypeScript

packages/shared-utils/src/format.ts（新增）
/** 格式化日期为 YYYY-MM-DD */
export function formatDate(date: Date | string): string {
  const d = typeof date === 'string' ? new Date(date) : date;
  const yyyy = d.getFullYear();
  const mm = String(d.getMonth() + 1).padStart(2, '0');
  const dd = String(d.getDate()).padStart(2, '0');
  return `${yyyy}-${mm}-${dd}`;
}

/** 格式化文件大小为人类可读格式 */
export function formatFileSize(bytes: number): string {
  if (bytes === 0) return '0 B';
  const units = ['B', 'KB', 'MB', 'GB', 'TB'];
  const i = Math.floor(Math.log(bytes) / Math.log(1024));
  return `${(bytes / Math.pow(1024, i)).toFixed(1)} ${units[i]}`;
}
packages/shared-utils/src/types.ts（新增）
/** 通用 API 响应结构 */
export interface ApiResponse<T = unknown> {
  code: number;
  message: string;
  data: T;
}

/** 分页参数 */
export interface PaginationParams {
  page: number;
  pageSize: number;
}

/** 用户基础信息 */
export interface UserInfo {
  id: number;
  name: string;
  email: string;
  avatar?: string;
}
packages/shared-utils/src/index.ts（更新后）
// 工具函数
export { formatDate, formatFileSize } from './format';
export { greet, add } from './utils';

// 类型定义
export type { ApiResponse, PaginationParams, UserInfo } from './types';
4

在 admin 中引用 — 享受完整的类型提示

apps/admin/src/App.vue（片段）
<script setup lang="ts">
import { formatDate, formatFileSize } from '@my-monorepo/shared-utils';
import type { UserInfo } from '@my-monorepo/shared-utils';

// IDE 会给出完整的智能提示！⌨️

  id: 1,
  name: '张三',
  email: 'zhangsan@example.com',

在 admin 项目中 Ctrl+Click 点击 formatDate，IDE 应该直接跳转到 packages/shared-utils/src/format.ts。
这就是 Monorepo + workspace 链接 + TypeScript 的"丝滑体验"。

5. 依赖管理进阶 — 什么依赖放哪里

依赖类型 放在哪里 示例
全局开发工具 根目录 devDependencies typescript, eslint, prettier, husky
某个包的运行时依赖 该包的 dependencies vue（在 admin 中）, express（在 server 中）
某个包的开发依赖 该包的 devDependencies vite（在 admin 中）, vitest（在 shared-utils 中）
共享包引用 使用方的 dependencies "@my-monorepo/shared-utils": "workspace:*"
多个包都需要的同一依赖 各自声明 + pnpm 去重 lodash 被 admin 和 server 都需要
💡 pnpm 的依赖提升策略

pnpm 默认不提升依赖（与 npm/yarn 不同），每个包的依赖严格隔离。 这意味着你不用担心"幽灵依赖"——在 admin 里能 import 的东西，一定在 admin 的 package.json 里写了。

如果确实需要某个依赖在所有包中都可用（罕见情况），可以在 .npmrc 中配置 public-hoist-pattern[]=*，但不推荐。

6. 共享配置包 — ESLint & Prettier 统一

除了共享业务代码，Monorepo 更大的价值在于共享配置。这是进阶用法， 先理解思路即可：

📦 概念：把配置也打包

创建一个 packages/eslint-config 包，导出统一的 ESLint 规则。
各子项目只需 extends: ['@my-monorepo/eslint-config']。
改一处，全项目生效。这就是 Monorepo 的治理能力。 

// packages/eslint-config/index.js（示意）
module.exports = {
  root: true,
  env: { browser: true, node: true, es2022: true },
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended',
    'prettier',
  ],
  parser: '@typescript-eslint/parser',
  rules: {
    'no-console': 'warn',
    '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
  },
};
⚠️ 注意

共享 ESLint 配置包通常需要发布到 npm 或使用 workspace:* 协议。 但 ESLint 的 extends 解析机制比较特殊，直接用 workspace:* 可能不工作，需要配合 require.resolve 或使用扁平配置（flat config）。这个坑在进阶阶段再展开。
